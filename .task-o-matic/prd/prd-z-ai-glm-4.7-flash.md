# Product Requirements Document: Arcade Vibe

**Document Version:** 1.0
**Author:** Product Team
**Date:** October 26, 2023
**Product Status:** Concept / MVP Definition

---

## 1. Overview

### 1.1 Executive Summary
**Arcade Vibe** is a competitive, gamified platform for prompt engineering disguised as a retro arcade interface. The core product allows users to submit "One-Shot" prompts to generate playable web-based games via AI. It acts as a meta-game where the goal is to win a leaderboard by engineering the most efficient, high-quality, and difficult-to-implement prompts. Unlike standard coding tools, Arcade Vibe monetizes strategy (choosing model difficulty) and efficiency (prompt length), creating a community of prompt engineers and players.

### 1.2 Problem Statement
Current prompt engineering tools lack competitive structure and quantifiable success metrics. Prompt engineers and AI enthusiasts struggle to measure the effectiveness of a prompt against others or to understand "risk/reward" strategies (e.g., "Can a tiny model beat a giant model if the prompt is perfect?"). There is a lack of a sustainable "arena" where prompt engineering skills can be honed, tested, and archived.

### 1.3 Value Proposition
*   **For Engineers:** A portfolio of their evolution as a prompt engineer, recognition for efficiency, and a new competitive sport to master.
*   **For Players:** A diverse library of games to play and rate, with insight into the "AI magic" behind them (via revealed prompts).
*   **For the Community:** A transparent, open-source library of high-performing prompts that benefit all users.

## 2. Objectives

### 2.1 Key Goals
*   **MVP Launch:** Launch the core competitive loop (Prompt -> Game -> Play -> Rate -> Score).
*   **Gamification:** Implement the scoring formula that rewards model difficulty and prompt efficiency.
*   **Community Governance:** Establish the mechanics for "Forking" and iterating on prompts.
*   **Engagement:** Encourage monthly active participation with a "Next Challenge" drop system.

### 2.2 Success Metrics (KPIs)
*   **Engagement:** Average session duration per game (Target: >5 mins).
*   **Quality:** Percentage of submitted games rated ≥4.0 stars (Target: >30%).
*   **Virality:** Ratio of "Prompt Runs" (users playing via other users' prompts) to Original Submissions.
*   **Retention:** Month-to-Month retention rate of active prompt engineers (Target: >40%).
*   **Innovation:** Diversity of models used in submissions (Target: <50% using only "Cheater" models).

## 3. Target Audience

### 3.1 User Personas

**Persona 1: The "Glitch Hunter" (Prompt Engineer)**
*   *Description:* An expert in LLM prompting, constantly seeking efficiency and edge cases. They enjoy the challenge of squeezing quality out of weak models.
*   *Motivation:* High ratings, competition with peers, and proving their prompt engineering is superior to coding.

**Persona 2: The "Retro Gamer" (Player)**
*   *Description:* Someone who enjoys classic arcade games. They are not necessarily technical but are drawn to the unique challenges each month.
*   *Motivation:* Entertainment, contributing to the leaderboard, and discovering how AI thinks.

### 3.2 User Stories

*   **As an Engineer:** I want to write a prompt, select a model (e.g., "Hard Mode"), and submit it once.
*   **As an Engineer:** I want to see a side-by-side comparison of how my prompt performs on GPT-5 vs. Haiku.
*   **As a Player:** I want to play a game generated by a prompt and rate it.
*   **As a Player:** I want to view the exact prompt used to generate a game to learn from it.
*   **As an Engineer:** I want to "fork" an existing winning prompt to iterate and improve it for the next month.

## 4. Features

### 4.1 Core Features (MVP)

#### 4.1.1 The "Arcade" Dashboard
*   **Description:** A retro-themed landing page featuring the current Monthly Theme and a leaderboard.
*   **Acceptance Criteria:**
    *   Displays countdown to Month End.
    *   Highlights Top 10 "Cheaters" (Winning on hard models) and Top 10 "Efficiency Kings" (Shortest prompts with high ratings).
    *   "Next Month" teaser section.

#### 4.1.2 Prompt Editor & Submission System
*   **Description:** The central workspace for creating prompts.
*   **Acceptance Criteria:**
    *   **One-Shot Enforcement:** Text area is optimized for single-block submission. No visual file uploads.
    *   **Model Selector:** Dropdown interface with defined categories:
        *   *Cheater (Opus-4.6):* 1.0x multiplier.
        *   *Normal (Kimi-k2.5):* 1.5x multiplier.
        *   *Hard (Haiku-4.5):* 2.5x multiplier.
        *   *Impossible (Tiny):* 5.0x multiplier.
    *   **Environment Config:** Hidden inputs for "Scoring System", "Lives", "Levels" (defined by the Monthly Theme, not user choice).
    *   **Validation:** Uses Zod 4 to ensure prompt length > 0 and < 5000 chars (Scoring calculation). JSON payload submission.

#### 4.1.3 Multi-Model Simulation
*   **Description:** A feature allowing the user to test their prompt against 2-3 different models simultaneously before final submission.
*   **Acceptance Criteria:**
    *   User inputs text.
    *   User selects models.
    *   UI renders a grid of iframes.
    *   Errors or NaNs are handled gracefully (prompt failed to generate).
    *   *Note:* Each simulation consumes API credits based on the model selected.

#### 4.1.4 Game Runner (The "Arena")
*   **Description:** A secure iframe sandbox where users play generated games.
*   **Acceptance Criteria:**
    *   Secure sandboxing to prevent external redirects or access to parent window.
    *   Playtime tracking logic (JavaScript integration on the client-side, aggregated to the server).
    *   "Rate Game" modal triggers upon session end or game completion.

#### 4.1.5 Scoring Engine
*   **Description:** Backend logic that aggregates data to calculate the final score.
*   **Formula:**
    *   `Score = (Avg_Rating * 50) + (Model_Multiplier * 20) - (Prompt_Length_Score) + (Playtime_Score) + (Vote_Volume)`
*   **Acceptance Criteria:**
    *   Calculation runs automatically at Month End.
    *   Scores are immutable after Month Freeze.

### 4.2 Future Features (Post-MVP)

*   **Prompt Marketplace:** Users can sell their winning prompts to subscribers.
*   **Team Mode:** Simultaneous editing of a single prompt.
*   **Prompt Analytics:** Heatmaps of words that trigger better game mechanics.
*   **Archive Mode:** A browseable library of "All Time" masterpieces (not ranked, just sorted by date/theme).

## 5. Technical Requirements

### 5.1 Tech Stack (Strict)
*   **Frontend:** Next.js 16 (App Router), Tailwind v4.
*   **UI Components:** shadcn/ui (customized for retro aesthetic).
*   **API Layer:** tRPC v11 (Type-safe, minimal overhead).
*   **Database:** PostgreSQL 18, Drizzle ORM.
*   **Authentication:** Better Auth.
*   **Validation:** Zod 4.
*   **AI Integration:** Vercel AI SDK v6 (Server-side calls).
*   **Styling:** Tailwind v4 + Custom CSS for CRT/Glow effects.

### 5.2 System Architecture

**Flow:**
1.  **Client:** User submits prompt + Model Selection via tRPC `rpc.createPrompt()`.
2.  **Backend API (tRPC):** Validates input (Zod).
3.  **AI Service (Vercel AI SDK):**
    *   Sends prompt to selected LLM (OpenAI/Anthropic/OpenRouter).
    *   Receives raw HTML/JS string.
    *   Saves generated game assets (HTML/CSS/JS) to Object Storage (e.g., S3/R2).
4.  **Database (Drizzle):** Records prompt metadata (ID, user, model used, prompt text hash, status).
5.  **Playback:** Frontend loads HTML file via a CORS-friendly proxy or iframe container.
6.  **Analytics:** Client-side `postMessage` or custom event tracking sent back to backend via API route to update playtime statistics.

### 5.3 Security & Performance

*   **Security:**
    *   **XSS Protection:** Sanitize AI-generated HTML output before serving in the iframe (DOMPurify).
    *   **Rate Limiting:** Strict limits on AI API calls per user to prevent quota abuse.
    *   **Auth:** OAuth 2.0 via Better Auth (Social providers).
*   **Performance:**
    *   **Streaming:** The UI should stream the AI response (conceptually, though "One-Shot" implies a wait, the feeling of processing should be real-time).
    *   **Database Indexing:** Index `userId`, `createdAt`, and `score` for fast leaderboard queries.
    *   **Caching:** Cache generated HTML files to minimize cold starts.

## 7. Open Questions / Risks

### 7.1 Open Questions
1.  **Run-time Playtime Tracking:** Should the platform track playtime via `performance.now()` in the generated iframe, or rely on the iframe's exit event? *Decision:* Exit event is more reliable but requires coordination.
2.  **API Key Management:** Should the platform pay for AI costs (SaaS model) or let users bring their own key (BYOK)?
    *   *Recommendation:* BYOK for MVP to reduce costs; user provided key is needed for "Run other people's prompts on *your* API key" feature.
3.  **Prompt Theft:** How do we hash prompts to prevent cheating by just copying the text string? *Recommendation:* Add a salt/hash on save; submitting a duplicate prompt should be discouraged or blocked.
4.  **Game "Fail States":** What happens if the AI generates broken HTML? *Decision:* If generation fails (error code), user must fix prompt.

### 7.2 Risks
1.  **Semantic Versioning of Models:** The prompt references "GPT-5.3" and "Haiku-4.5." We need a flexible abstraction layer in the API to handle different provider capabilities.
2.  **Content Moderation:** LLMs often generate NSFW code or `eval()` statements. The prompt says "Zero context," but the platform *must* have a moderation layer (human review or automated script) before a game is made public.
3.  **Scalability of Leaderboards:** If 1,000 people submit games a month, sorting by score requires Redis or heavy DB indexing optimization.
