# Product Requirements Document: Arcade Vibe

## 1. Overview

### Executive Summary
Arcade Vibe is a competitive platform for prompt engineers, themed as a retro arcade. Users compete in monthly challenges to generate fully playable games via a "one-shot" prompt (a single message with no conversation history). The platform focuses on the skill of prompt engineering rather than traditional coding. Participants choose AI models of varying difficulty as a handicap mechanism, where harder (smaller) models offer higher score multipliers.

### Problem Statement
Currently, there is no dedicated competitive venue for "one-shot" prompt engineering. Most AI coding tools assist via multi-turn conversations, diluting the raw skill of crafting a perfect single instruction. There is no standardized leaderboard to compare how well different users can instruct AI to build complex, functional software (games) under constraints.

### Value Proposition
*   **For Prompt Engineers:** A competitive arena to prove skill, experiment with model constraints, and build a public portfolio of prompt evolution.
*   **For Players:** An endless stream of free, community-generated games with a "retro arcade" experience.
*   **For the AI Community:** Radical transparency via public prompt histories, allowing analysis of what makes specific models succeed or fail at code generation.

---

## 2. Objectives

### Business & Technical Goals
1.  **Gamify Prompt Engineering:** Transform the tedious task of prompt refinement into a competitive sport with a monthly seasonal structure.
2.  **Standardize Evaluation:** Create a fair, anti-gaming scoring algorithm that balances quality (ratings), difficulty (model choice), and efficiency (prompt length).
3.  **Ensure Playability:** Enforce strict technical standards so every generated game is playable, responsive, and secure (iframe-compatible).

### Success Metrics (KPIs)
*   **Engagement:** Average play session length > 3 minutes per game.
*   **Quality:** > 40% of submitted entries achieve a rating ≥ 4 stars.
*   **Retention:** > 50% of Month 1 participants return for Month 2.
*   **Virality:** Ratio of "Prompt Runs" (using others' prompts) to Original Submissions > 0.3.

---

## 3. Target Audience

### User Personas
1.  **The Architect (Prompt Engineer):** A technical user proficient in LLMs. Motivated by ranking, technical challenges, and demonstrating control over "unpredictable" models.
2.  **The Gamer (Casual Player):** Visits the arcade to play. Doesn't necessarily prompt. Motivated by fun, novelty, and rating games.
3.  **The Researcher (Data Analyst):** Interested in comparing model capabilities (e.g., GPT vs. Claude vs. DeepSeek) using a standardized benchmark.

### User Stories
*   **As an Architect**, I want to select a specific "Impossible" difficulty model so I can maximize my score multiplier if I succeed.
*   **As an Architect**, I want to see the diff between my v1 and v2 prompts so I can track my evolutionary strategy.
*   **As a Gamer**, I want to play a game in an iframe without it crashing my browser or accessing my cookies.
*   **As a User**, I want to use my own API key to run a public prompt on a model the original author didn't use, to test portability.

## 4. Features

### 4.1 Core Features (MVP)

#### A. The Monthly Challenge & Theme System
*   **Description:** A global state manager that tracks the current month, theme description, and countdown timer. At month-end, the leaderboard freezes, and a new theme is instantiated.
*   **Acceptance Criteria:**
    *   System automatically transitions to a new theme on the 1st of every month (00:00 UTC).
    *   Previous months' games are archived but remain playable with "Frozen Rank" badges.
    *   Themes include mandatory constraints (e.g., "Must include a scoring system," "Must support mobile touch").

#### B. The Prompt Lab (Creation Interface)
*   **Description:** The interface where users craft their one-shot prompt.
*   **Model Selection:** Dropdown categorized by difficulty:
    *   *Cheater:* GPT-5.3, Opus-4.6 (Low Multiplier)
    *   *Normal:* GLM-4.7, Kimi-k2.5 (Medium Multiplier)
    *   *Hard:* Deepseek-3.2, GPT-5.1-mini (High Multiplier)
    *   *Impossible:* Tiny Models (Highest Multiplier)
*   **Multi-Model Execution:** Checkbox option to run the same prompt on up to 3 models simultaneously for side-by-side comparison (consumes API quota).
*   **Acceptance Criteria:**
    *   Input is a single text block (no chat history).
    *   System enforces "Core Requirements" injection (system prompt appending) transparently.
    *   "Run" triggers the AI SDK stream and renders the result in a sandboxed preview.

#### C. The Sandbox (Game Runner)
*   **Description:** A secure environment to render the HTML/JS/WASM generated by the AI.
*   **Security:** Must strip cookies, prevent external network requests (unless specific APIs allowed), and block alert/confirm/prompt dialogs.
*   **Acceptance Criteria:**
    *   Generated code runs in a strict iframe with `sandbox="allow-scripts allow-same-origin"` (using a blob URL or srcdoc).
    *   Content Security Policy (CSP) prevents calls to unauthorized external domains.
    *   Responsive design testing (Toggle Desktop/Mobile view).

#### D. Dynamic Scoring Algorithm
*   **Description:** Backend logic to calculate the "Arcade Score."
*   **Formula Inputs:** Average Star Rating, Model Difficulty Multiplier, Prompt Length (Inverse logarithmic scale), Unique Play Count.
*   **Anti-Gaming:** Prompt Brevity Score (PBS) penalizes copy-pasting entire code libraries into the prompt.
*   **Acceptance Criteria:**
    *   Score updates in near real-time as new ratings come in.
    *   If prompt length > 2000 chars, score efficiency penalty applies.

#### E. User Profiles & Prompt Genealogy
*   **Description:** Profile pages showing a user's creations and their "Prompt Runs" (re-executions of others' prompts).
*   **Privacy Controls:**
    *   *Private:* Only visible to author.
    *   *Public EOM:* Visible after the month ends.
    *   *Full Public:* Visible immediately.
*   **Acceptance Criteria:**
    *   Users can fork their own previous prompts to create a new version.
    *   "Genealogy View" visualizes the prompt diff between versions.

### 4.2 Future Features (Post-MVP)
*   **BYOK (Bring Your Own Key):** User settings to input personal API keys for infinite "Prompt Runs" on other models.
*   **Model Leaderboard:** Aggregated stats showing which models generate the highest-rated games.
*   **Live Jams:** 24-hour sprints with specific constraints.

## 5. Technical Requirements

### Tech Stack (Strict Constraints)
*   **Framework:** Next.js 16 (App Router)
*   **API Layer:** tRPC v11
*   **Database:** PostgreSQL 18 managed via Drizzle ORM
*   **Authentication:** Better Auth
*   **Styling:** Tailwind CSS v4 + shadcn/ui
*   **AI Integration:** Vercel AI SDK v6 (standardized interface for multi-provider)
*   **Validation:** Zod 4

### System Architecture Overview
1.  **Next.js Server Actions / tRPC Routers:** Handle prompt submission, scoring logic, and theme retrieval.
2.  **AI Worker:**
    *   Receives prompt + system constraints.
    *   Calls provider API (OpenAI/Anthropic/etc.) via Vercel AI SDK.
    *   Returns streamed text/code.
3.  **Sandbox Service:**
    *   A specialized route that renders the user's HTML/JS game inside a secure wrapper.
    *   Handles "responsiveness" checks (emulated viewport injection).
4.  **Postgres DB:**
    *   `Users`, `Games`, `Prompts` (linked to Game), `Ratings`, `Themes`.

### Security & Performance
*   **Sandbox Isolation:** Games must run in an isolated origin or strict iframe sandbox to prevent XSS attacks on the main platform.
*   **Prompt Injection Defense:** System prompts defining the "Core Requirements" must be distinct from user input to prevent users from overriding the rules.
*   **Cost Management:** Implement rate limiting on AI generation per user tier to prevent API budget exhaustion.

## 7. Open Questions / Risks

### Ambiguities
*   **Model Access:** How do we authenticate "Impossible" tier models? Do we host them or require user API keys for that specific tier?
*   **Game File Size:** What is the maximum size for generated code? (E.g., if the LLM generates a 5MB Base64 asset string, the DB and UI will choke).

### Potential Blockers
*   **Sandbox Security:** If a generated game creates a loop that crashes the browser tab, does it affect the parent app? (Solution: likely needs a separate worker or iframe origin).
*   **AI Hallucination:** High rate of non-playable generations might discourage users. Need a "Retry" mechanism that doesn't count as a "New Shot" or allow minor manual bug fixing? (Strict vision says no, UX says maybe yes).
*   **API Costs:** Running prompts on "Cheater" models (Opus/GPT-5) is expensive. Monetization strategy required to cover API costs for high-volume users.
